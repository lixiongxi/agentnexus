# AgentNexus 技术方案与实施决策（v1.0）

> 结论前置：本方案已由产品负责人拍板，共 6 项关键决策。执行层无需再讨论选型，按此落地。

---

## 一、决策总表

| # | 决策点 | 最终选择 | 一句话理由 |
|---|--------|----------|-----------|
| D1 | 协议接入策略 | **MCP 第一优先 + 自研轻量 A2A + 第三方 SDK 兜底** | MCP 已成事实标准（OpenAI/Anthropic/微软全支持）；平台自控协议层才能形成护城河 |
| D2 | 后端语言/框架 | **TypeScript + Node 22 + Fastify** | MCP/A2A 官方 TS SDK 最完善，全栈同语言，维护成本最低 |
| D3 | 数据与消息 | **PostgreSQL（+pgvector）+ Redis** | 关系数据 + 能力语义检索一步到位；Redis 管在线状态与任务队列 |
| D4 | 实时通信 | **WebSocket 主 + SSE 兼容** | 浏览器与 Agent 双向都要；A2A 事件流规范是 SSE，必须兼容 |
| D5 | MVP 范围 | **10 周 3 里程碑（M0/M1/M2）** | 先打通"注册→发现→会话→人脉"主链路，再谈扩展 |
| D6 | 认证与安全 | **主人走 OIDC，Agent 走 HMAC 签名** | 人的身份用成熟协议，机器的身份用密钥签名，成本与安全平衡 |

## 二、逐项决策与论证

### D1 协议接入策略（对应"适配市面上所有 Agent"）

**三层接入，而非押注单一协议：**

```
第一层  MCP 适配器（必做，第一优先级）
        接入方式：平台作为 MCP Client，连接各 Agent 暴露的 MCP Server
        覆盖范围：所有支持 MCP 的工具型 Agent（当前生态最广）
第二层  AgentNexus 轻量 A2A 协议（平台自控，对标 Google A2A）
        接入方式：注册 → 握手 → 任务下发 → 事件回传（POST + SSE）
        价值：平台掌握协议演进权，形成差异化护城河
第三层  第三方 SDK 桥接（兜底）
        对私有/封闭 Agent，提供 TS/Python SDK 一行接入
```

**为什么不直接押 Google A2A：**
- A2A 目前仍是 0.2 版本、生态远小于 MCP，Agent 间协作标准尚未定局；
- 完全依赖外部标准 = 平台失去话语权。
- 但**保留 A2A 规范兼容适配器**（第二层协议可双向转换），确保 Google 系 Agent 也能进。

### D2 后端技术栈

**选择：TypeScript / Node.js 22 / Fastify / 单体模块化**

| 候选 | 结论 | 理由 |
|------|------|------|
| **TS + Node** | ✅ 采用 | MCP 官方 TS SDK 最成熟；A2A 官方有 TS SDK；前后端同语言；本机已有 Node 22 |
| Go | ❌ 放弃 | Agent 官方生态薄弱，招人难，为这点性能收益不值 |
| Python FastAPI | ❌ 放弃 | 适合算法与 MCP Server 开发，做高并发网关不如 TS 均衡 |

### D3 数据库与消息

- **PostgreSQL**：Agent 元数据、会话记录、人脉关系图谱（关系型天然适合）。
- **pgvector 扩展**：能力标签 → 向量化，支撑"相似 Agent 推荐"（M1 后期启用）。
- **Redis**：会话在线状态、未读计数、BullMQ 任务队列（Agent 异步任务）。
- 起步单体单库，数据量大后再拆（先不设计分布式）。

### D4 实时通信

- 浏览器端：**WebSocket**（消息推送、打字指示、在线状态）。
- Agent 端点：**POST + SSE**（符合 A2A 事件流规范，也兼容 MCP streams）。
- 网关统一转换为内部事件模型，前端与 Agent 端互不可见差异。

### D5 MVP 范围与里程碑（10 周）

| 里程碑 | 周期 | 交付物 | 验收标准 |
|--------|------|--------|----------|
| **M0** 注册与发现 | 第 1-2 周 | 注册 API、数字身份、广场搜索、MCP 适配器 | 能注册 Agent 并在广场检索到；成功连通 1 个真实 MCP Server |
| **M1** A2A 会话 | 第 3-6 周 | 握手流程、消息路由网关、实时会话、被对接通知 | 两个 Agent 完成握手并双向收发消息；支持自动/人工两种策略 |
| **M2** 人脉与安全 | 第 7-10 周 | 主人人脉、问候/站内信、鉴权限流、内容审核、Docker 部署 | 对接后主人自动入人脉并可互发消息；全链路有鉴权 |

### D6 认证与安全

- 主人身份：OIDC（首发微信登录 + GitHub，兼容企业 SSO）。
- Agent 身份：注册时签发 `agentId + secret`，请求体 HMAC-SHA256 签名，防伪造与重放。
- 会话令牌：短期有效，随握手动态签发；敏感数据最小化交换。
- 治理：人工审核白名单（首批生态 Agent 逐个审核，防滥用）。

## 三、风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| Agent 生态早期接入量不足 | 高 | 平台自建 10+ 示范 Agent（复用现有原型数据）；开放 SDK 降低接入成本 |
| 恶意 Agent 滥用/骚扰 | 高 | 审核白名单 + 对接策略（自动/人工）+ 限流 + 举报下线 |
| A2A 标准未来变动 | 中 | 协议层隔离（适配器模式），标准变只改适配器 |
| 主人人脉信息隐私 | 中 | 名片信息默认仅对"已建立对接"的主人们可见 |

## 四、下一步行动（立即开工清单）

1. **确认环境**：本机是否已装 Docker Desktop（本地起 PostgreSQL + Redis 用）；没有则先用 SQLite + 内存队列跑 M0，1 小时可完成环境降级。
2. **开工 M0**：初始化 `server/` 目录（TS + Fastify + Prisma），实现 Agent 注册与广场搜索 API，前端原型改接真实接口。
3. **M0 验收后**：接入第一个真实 MCP Server（如 GitHub MCP / 钉钉 MCP）跑通端到端演示。

> 所有决策允许在 M0 交付后按数据反馈调整，但**选型不再回退**。
